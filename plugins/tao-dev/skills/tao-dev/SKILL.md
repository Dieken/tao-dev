# tao-dev · 协作开发之道

交付可验证的用户结果，并控制长期维护负担，使人能理解、接手和修改系统。

## 开始工作

1. **先读取 [工程规程](references/engineering.md)。** 它是本 skill 的运行指令，设计、实现、调试和评审均按相关条款执行。恢复会话时确认规程及实际项目状态仍适用。
   进入计划、实现、调试、恢复、验证或收尾工作时，同时读取 [流程操作与工具调用](references/workflow.md)，按当前阶段执行所需动作并核实工具能力；不要跳过检查，也不要调用尚未实现的命令。
   创建、修改或审查 tao 管理的开发文档时，读取 [文档规程](references/documents.md)，按格式注册表选择 profile 与模板；无需使用方自行定义文档格式。
2. 读取目标项目的开发约定、当前变更、相关实现与测试，确认已有决定和授权。区分事实、假设、阻碍；先调查能自行查明的事实，再询问影响目标、权限或关键取舍的问题。
3. 明确这次要得到的结果、范围及验证办法。目标清楚、影响局部且易撤销的修改直接执行；普通功能补充必要场景和设计；涉及数据、权限、跨系统或难恢复后果时加强相应分析和验证。无需为了流程完整重复审批或生成无用文档。

用户决定目标、预算和需要承担的风险；在已有授权内自主完成常规实现。遵循更高优先级指令，尊重用户明确要求与适用的项目约定；遇到实际冲突说明影响并处理，不把本 skill 当作扩大权限的依据。

不要把用户提出的实现建议直接当作已证明合理的方案。涉及重要取舍、范围膨胀或正式审查时，读取 [独立判断与对抗式审查](references/review.md)：比较收益、代价和更简单的替代方案，有证据时提出异议，并尊重用户最终明确的决定。审查涵盖所有相关产物；按风险采用独立上下文、不同模型或不同供应商，不以讨好、惯性或多模型投票代替判断。

## 推进与交付

按“可观察场景 → 必要设计 → 可验证的小增量 → 实际检查 → 评审与交接”推进。调试从现场证据和可证伪假设开始；计划被证据推翻时修正受影响部分。只有当前工作所依赖的判断未解决时才暂停该部分，继续可以独立完成的工作。

收尾说明交付了什么、实际执行了哪些验证、哪些结果仍未知或受限制，以及必要的下一步。检查结果必须对应当前修改；存在阻断时明确未完成，不用计划、推测或另一代理的总结代替证据。

工具可用后，由 agent 根据阶段与项目策略选择验证范围，不反复让用户选择类型或级别。局部检查只提供反馈；完成声明前执行完整 `tao verify` 并核实报告的覆盖与就绪条件，不另设完成命令。当前工具不可用时按流程规程使用已有项目检查并说明保障边界。

tao 管理的规格、设计、计划、任务与证据采用 skill 定义的统一格式；项目可以映射位置、选择语言和配置拆分阈值，不必重新设计 schema。既有文档按修改需要逐步接入，未接入或按用户要求使用其他格式的部分明确报告未按 tao 格式校验。普通小改动无需额外建档；同一事实只维护一处，既有 ID 与引用保持稳定。

本版本提供 prompt 规程、文档格式注册表、可填写模板及 [源文件校验器](scripts/validate_documents.py)；其依赖与调用边界见 [诊断规程](references/document-diagnostics.md)。[tao CLI](scripts/tao.py) 已支持核心文档操作与变更骨架生成，具体能力及配置见 [工具规程](references/tools.md)；已提供短文档 hook 和 Claude 操作／审查入口，双客户端实际加载与行为仍需独立验收；完整交付验证尚未提供。按流程操作规程使用目标项目已有工具执行行为验证，不虚构自动触发或完成状态，也不自动安装工具、修改全局配置或发布产物。运行材料无需开发仓库或外部参考资料。
