# tao-dev · 协作开发之道

交付可验证的用户结果，控制长期维护负担，使人能理解、接手和修改系统。

## 开始工作

1. **先读取 [工程规程](references/engineering.md)。** 进入计划、实现、调试、恢复、验证或收尾时，同时读取 [流程操作](references/workflow.md)，按当前阶段执行。
2. 读取目标项目约定、当前变更、相关实现与测试，确认已有决定和授权。先调查能自行查明的事实，再询问影响目标、权限或关键取舍的问题；恢复会话时核实实际状态。
3. 明确结果、范围及验证办法。目标清楚、影响局部且易撤销的修改直接执行；普通功能补充必要场景和设计；数据、权限、跨系统或难恢复的修改加强分析与验证。

用户决定目标、预算和承担的风险；在已有授权内自主推进，遵循更高优先级指令和项目约定。只有当前工作依赖的判断未解决时才暂停该部分，继续可独立完成的工作。

## 按任务读取参考

| 当前任务 | 读取入口 |
|---|---|
| 创建、修改或审查 tao 管理文档 | [文档规程](references/documents.md)，再选择本次使用的模板与补充规程 |
| 重要取舍、范围膨胀或正式审查 | [独立判断与审查](references/review.md)，比较收益、代价和更简单的替代方案 |
| 调用 tao CLI、配置项目检查 | 由流程规程进入 [工具规程](references/tools.md)；环境、验证与记录格式按操作需要读取 |

只需项目原生检查、既无 tao 文档同步职责也未绑定 tao 变更的局部代码任务，在工程与流程规程处停止。不要沿链接加载全部参考或未使用的模板。

## 推进与交付

按“可观察场景 → 必要设计 → 可验证的小增量 → 实际检查 → 评审与交接”推进。调试从现场证据和可证伪假设开始；新证据否定计划时修正受影响部分。

按流程规程选择检查范围，已接入完整交付判定的变更在完成声明前执行完整 `tao verify`。收尾说明交付内容、实际验证、未验证范围和必要下一步；证据必须对应当前修改，阻断未解则明确未完成。

普通小改动无需额外建档。受影响文档按职责同步，同一事实只维护一处，既有 ID 与引用保持稳定。工具只报告实际执行结果；安装依赖、修改全局配置或发布产物均须符合已有授权。
