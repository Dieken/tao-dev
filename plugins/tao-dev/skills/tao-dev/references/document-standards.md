# 文档格式的公共依据与写法

编写或审查需求、用例、决策和设计时读取本文。优先采用已有公开语法和成熟文档惯例，只有稳定引用、追踪或确定性校验需要时才增加 tao-dev 约定。本文随 skill 分发，提供填写模板所需的规则；链接用于核实出处，日常填写不依赖联网。

## 采用范围

| 内容 | 采用的依据 | 在 tao-dev 中如何使用 |
|---|---|---|
| 行为需求 | [EARS 作者说明](https://alistairmavin.com/ears/) | REQ 正文默认使用下述条件化句式；不把 EARS 扩大为文件组织标准 |
| 验收场景 | [Gherkin 的 Given／When／Then](https://cucumber.io/docs/gherkin/reference/) | UC 按前置条件、动作、可观察结果编写；MyST 中的 UC 不是可直接执行的 .feature 文件 |
| 架构决策 | [Nygard ADR](https://www.cognitect.com/blog/2011/11/15/documenting-architecture-decisions) | 沿用标题、状态、context、decision、consequences；使用全局 ID，保留替代关系 |
| 系统设计 | [arc42](https://arc42.org/overview/) | 按需覆盖边界、约束、结构、运行与部署、质量和风险；用既有 profile 的章节或子节承载，不强制复制整套目录 |
| 面向使用者的文档 | [Diátaxis](https://diataxis.fr/) | 区分教程、操作指南、参考、解释的阅读目的；按目的组织页面，避免同页混写学习教程与故障操作步骤 |

EARS 是受约束的自然语言写法，ADR、arc42、Diátaxis 是文档实践或框架；不能统一声称它们是正式认证标准。tao 的 profile、章节标记、全局 ID、关系字段和 JSONL 退役记录是本项目补充。MyST 承载正文，YAML 承载元数据，GFM 提供 checkbox 写法；这些公开语法并不自动认可 tao 的附加字段或渲染指令。

## EARS：先选条件，再写系统响应

先判断行为是否始终成立、由事件触发、在某状态持续成立、仅适用于某产品配置，或响应异常。不要为了填齐类型而虚构需求。下表为本项目的中文写作约定与原创示例，不声称是官方中文语法。

| 类型与英文关键词 | 中文写法与示例 |
|---|---|
| 普遍适用（Ubiquitous，无条件关键词） | “系统应……”：导出器应使用 UTF-8 编码输出文本。 |
| 事件驱动（Event-driven，When） | “当……时，系统应……”：当用户取消导出时，导出器应停止该次导出。 |
| 状态驱动（State-driven，While） | “在……期间，系统应……”：在只读模式期间，编辑器应禁止修改正文。 |
| 可选功能（Optional feature，Where） | “对于包含……功能的版本，系统应……”：对于包含离线功能的版本，阅读器应允许打开已下载的文档。 |
| 异常行为（Unwanted behaviour，If／then） | “如果……，则系统应……”：如果目标文件已存在，则导出器应拒绝覆盖该文件。 |
| 组合条件（Complex） | 按适用条件、状态、触发、响应组织：在只读模式期间，当收到保存请求时，编辑器应返回只读错误。 |

英文正文保留对应关键词及 shall，例如：When export is cancelled, the exporter shall stop that export. 中文使用“应”表示需求承诺；不要把 shall 翻译成可选建议。Where 指功能是否包含在产品配置中，不表示地理位置，也不等同于功能启用期间的 While 状态。

每条需求明确系统主体和可观察响应。EARS 本身允许一个或多个响应；tao 为独立追踪与验收，要求把可分别接受、修改或失败的承诺拆成多个 REQ，这属于本项目约定。验收必要的时间、容量和精度写成有单位、适用负载及测量条件的约束；缺少数值时记录未决项，不凭模型补造承诺。

需求是约束系统的承诺，用户故事可解释受益者与动机，但不能代替该承诺。纯粹的范围、术语、来源、设计理由不强套 EARS；公式、状态机或决策表更清楚时引用其唯一权威定义，并说明适用范围和判定方式，不把复杂规则硬塞进一句话。

## 填写模板而不重复事实

[REQ 片段](../assets/templates/req-block.md) 和 [规格模板](../assets/templates/spec.md) 共用同一组变量：REQ_BODY 放上述承诺；REQ_ACCEPTANCE 放验证输入、观察办法和通过判据，或引用已有 UC；REQ_SOURCE 放需求来源及必要动机。acceptance 不逐字重写正文，也不能悄悄新增正文没有的承诺。

例如，上表“目标文件已存在”的需求可在 acceptance 写“预先创建目标文件并记录内容校验和，执行导出，比较前后校验和；一致为通过”，source 写明实际的数据保护要求来源。不得把此例的假设来源或数值当成使用方项目的事实。

UC_GIVEN 写确定的初始条件，UC_WHEN 写触发动作，UC_THEN 写能观察或断言的结果；用 verifies 关联 REQ。测试已经采用 Gherkin 时，文档引用权威场景的位置和关联 ID，不手工复制一份易漂移的步骤；执行与否仍由真实测试证据证明。

ADR_CONTEXT 说明约束、备选和冲突，ADR_DECISION 写明确选择，ADR_CONSEQUENCES 写收益、代价和后续责任。架构文档复用这些 ADR；公共结构已有对应字段时，不再添加同义字段或另一套局部编号。

## 检查边界

结构、必填字段、ID 与引用由格式契约确定。语义审查另检查：状态与事件是否混淆、系统主体是否明确、响应是否可观察、多个承诺是否需要拆分、验收是否改变原需求。缺少英文关键词不能直接判定中文需求不合格；出现关键词也不能证明内容正确。

自动检查若只能发现可疑词句，应按文档诊断规程给出复查提示，不能声称完整解析 EARS 或通过语义验收。当前没有 EARS 语义检查器；执行型 Gherkin 场景需用项目实际测试工具验证。
