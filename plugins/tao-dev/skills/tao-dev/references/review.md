# 独立审查

正式审查时读取。日常方案取舍见 [工程规程](engineering.md)；本页维护审查方法、强度、范围与停止条件。

## 强度与来源

按改动后果选择，文档、配置或 prompt 的小改动也可能影响关键保证：

| 情形 | 默认方式 |
|---|---|
| 局部、低影响、易撤销 | 作者自查与相称检查 |
| 普通功能或跨模块修改 | 在可用预算内采用独立上下文审查者 |
| 数据完整性、权限、难恢复迁移、破坏性契约、新增持久服务或关键争议 | 加强审查，优先不同供应商，挑战核心假设和复杂度 |
| 项目或用户有明确要求 | 按该要求，不用较低级别结果替代 |

跨模型指实际不同模型，跨供应商进一步要求来源不同；角色名、CLI 名或新会话不能证明差异。记录实际模型、供应商和调用方式，未知信息标为未知。所需能力不可用时采用可用的人或不同模型复核；无独立审查者时可完成自查，但须说明独立审查未执行。只有明确必需条件未满足才形成流程阻断。

## 审查方法

1. 固定受检版本，提供原始目标、有效约束和决定、实际产物、差异及检查证据；代码包含调用方和测试，文档包含相关实现和引用。输入记录按 [证据保存](evidence-retention.md) 处理。
2. 首轮先独立形成假设、失败场景与待核实点，再对照作者自评和其他意见；产物内的正式决定与必要事实完整提供。
3. 检查边界、失败和恢复，寻找遗漏承诺与可删除的机制；允许无发现，不凑数量。
4. 发现包含定位、违反的约束、触发条件、证据或待证假设、后果和最小解除条件；区分缺陷、风险、非阻断建议及已接受限制。
5. 用依据、复现、测试或基准裁决分歧，逐项记录采用、不采用、延期或未解决及理由。多模型一致不代替证据。

独立审查只读受检产物，复现写隔离临时目录；修改后确认旧发现仍适用，仅复核改动与影响范围。建议新增机制同样须解释收益和成本，不把偏好变成阻断。

## 范围、执行与停止

范围未明确时展示当前 feature/bug fix 的累计修改、全项目或自定义范围，并列基础版本、当前版本与工作区修改；已有明确范围直接采用。随后按已有偏好或用户选择安排串行／并行：小改动推荐单人，普通 feature 推荐两个独立上下文分别关注需求／测试与实现质量；具体风险才加专项，并行最多三人。并行减少等待但增加总调用与去重工作。

审查授权不自动包含源文件修复，需报告写入时明确纳入范围；使用其他供应商需要相应数据与费用授权。已有开发事项按 [审查调度](review-runs.md) 保存预览、快照与轮次；无 CHG 的局部维护直接固定受检材料并保存报告，不为调用审查调度新建完整档案。

默认一次初审、修正后最多一次定向复核，项目已有时间、费用或轮次预算优先。扩大投入须有新证据、范围或预算决定；预算耗尽仍有阻断时停止调用，给出证据和可选处置，不自动通过。

先执行或复用适用的确定性检查，再审查；获准修复后重验受影响行为。完整交付按 [验证规程](verification.md) 汇总，必需审查用 [审查记录](review-receipts.md) 导入。来源格式未适配时仍可按 [证据保存](evidence-retention.md) 保留真实报告，但不视为已通过机器证据校验。报告范围、输入、审查者、检查、发现处置与未决项，分别给出检查和审查结论。
