# Agent 内开发流程

处理 setup、new、continue、refine、implement、review、debug、status、handoff、docs、finish 时读取。先遵守 [工程规程](engineering.md)；本文是动作与阶段的共享来源，客户端包装不另定流程。

## 入口与交互

Claude 使用 `/tao-dev:<动作>`，Codex 使用 `$tao-dev <动作>`；请求和动作写在同一条消息。主 skill 入口也接受自然语言并按当前目标分派。开始后可直接说“继续”“修改这里”等，不要求重复调用 skill。没有指定动作时先调查上下文，识别是新需求、修订还是恢复；只有目标仍不明确才询问。

- 先查项目、源码和已有决定，再问会改变目标、授权或关键取舍的问题。优先用客户端实际提供的原生选择/提问工具，推荐项说明理由并保留自由输入；不可用时用简短编号选项。不假定所有客户端和模式都有相同工具。
- 每个阶段开始写文件前确认本阶段写入范围。一个清楚的“同意，开始下一阶段”同时批准当前产物和下一阶段写入，不重复询问；“澄清完成”本身不等于允许写文件。已有明确覆盖后续工作的授权继续有效。
- 选项默认值、超时或没有回答不等于批准。把相关选择合并，不让用户回答能够自行查明的问题。实现开始后在已批准范围内自主完成，只为重大范围/方案变化、必要的人类决定或有限重试仍无法解除的阻断暂停。
- 有原生 task/todo 工具时把实际阶段及执行任务映射进去；持久任务以文档为准，UI 列表可重建。每个阶段告一段落时说明当前阶段、完成事项、待做事项、阻断和下一步，链接实际产物。

调用 CLI 前按 [工具规程](tools.md) 定位已安装的运行入口并运行 doctor；不用 PATH 猜同名程序。需要准备工具依赖时才读 [运行环境](runtime.md)。以下动作都由 agent 在会话内调用工具，用户无需转到 shell。配置缺失不会迫使用户重装；需要时在已确认写入范围内接入最小项目配置。

## setup：可选的项目接入

按 [项目接入](project-setup.md) 只读探测已有技术栈、工具、CI 和配置，给出最小接入与工具补充选项；获准后配置并执行约定基线，报告实际文件和检查结果。空项目不猜技术栈或安装工具。重复调用检查和补充，不重置约定。完成后提示 new，已有任务则提示 continue。

## new：从业务需求开始

1. 用户只需描述业务需要。调查已有行为、相似实现、规格和设计，用少量问题澄清范围、场景和验收；工程规范、路径、文件名和文档语言由 agent 按项目约定处理。
2. 总结明确的需求与未决点，请用户确认澄清是否完成，以及是否允许创建工作副本和编写 spec。意见未收敛时继续讨论，不抢先创建文档。用户可把两项确认一次给出。
3. 按 [工作流状态接口](workflow-state.md) 执行 workflow start，默认在项目根 `.worktrees/` 创建 Git worktree 和 feature branch。复用现有隔离副本；记录实际根、分支和比较基准。缺初始提交、未处理修改或目标冲突时先解释具体情况，不丢弃现有工作。
4. 在隔离副本中创建或更新适用 spec，保存检查点，运行文档检查，返回可点击文件链接。请用户查看并选择提出修改，或批准开始 design。不要在 new 中一次写完全部文档和代码。

创建和修改正式文档时读取 [文档规程](documents.md) 与当前所需模板；位置与组织统一见 [文档组织](document-layout.md)。采用完整 feature 流程时，spec、design、plan 分别有明确文档入口；可以复用现有文件。极小文案或局部维护不必额外建完整档案，但不能擅自把已开始的完整流程降级。

## continue：推进或恢复

先读取 workflow status 和项目实际状态，按照 [状态与接续接口](workflow-state.md) 恢复；不要只信任会话摘要或 handoff。确认对应 worktree、现有文件、有效批准、任务进度、证据时效和仍在运行的操作，保留部分实现并避免重复启动进程。没有 handoff 也能从检查点与产物继续；尚未持久化且已丢失的讨论需要补充，不能推断批准。

| 当前阶段 | 获准后的工作 | 阶段结束与下一步 |
|---|---|---|
| spec | 澄清后的业务范围、REQ/UC、可判定验收与必要问题 | 展示 spec，修改或批准 design |
| design | 读取 spec，选择最小方案，说明接口、约束、失败与验证设计 | 展示 design，修改或批准 plan |
| plan | 读取已批准规格与设计，生成实施计划及可验证 TASK、依赖和检查办法 | 展示 plan/tasks，修改、文档审查或批准实现 |
| implement | 按批准任务自主实现代码和测试，更新真实进度与证据 | 总结实现和检查，提示 review |
| review | 根据确认范围组织实际审查及检查 | 问题需修订/修复；通过后提示 finish |
| finish | 执行用户选中的整理、合入、推送和清理 | 说明实际完成事项和保留内容 |

文档每个阶段在内容和格式可供检查后都停在用户检查点。用户提出意见时留在该阶段修订，不能把意见当作批准。没有阶段写入批准时，continue 展示拟进行的工作并询问；已有有效批准时继续该范围，无需重复批准。

编写 plan 时才调用 `tao new --slug <原 slug> --change <CHG-ID>`，填完骨架再检查；不要在 spec 阶段生成空计划来满足工具。用户尚未做文档审查时，在进入实现前提供“先审查文档”和“跳过可选文档审查并开始实现”的选择；项目强制要求的审查不能跳过。已完成当前版本审查则不重复问是否需要审查。记录真实选择后推进阶段。

## refine：修订已有内容

根据用户意见和当前阶段定位 spec、design 或 plan，可在任何阶段回到已存在产物。先说明受影响的文件与下游工作，按已有或本次确认的范围写入。缩减业务范围同步规格、设计和任务；改变技术方案同步设计和计划；纯任务拆分只修改任务安排。用 workflow revise 使相应下游批准失效，保留现有代码和稳定 ID，不重建任务编号。

取消正式需求/任务/文档时按文档规程使用 retire 的只读预览，确认引用影响后在已有删除授权内应用。普通文件删除、移动、任务完成或 worktree 清理不等于退役。review 的“建议删除”本身不授权删除。修订完成展示差异和当前检查点，不自动进入实现。

## implement：自主完成批准的计划

读取计划、设计、需求和任务依赖，确认批准仍适用；还未完成文档阶段时回到对应检查点。以可验证的小增量实现，针对行为编写相称的单元/集成测试；按项目既有命令运行测试、静态检查和构建。只有实际检查支持时才勾选任务并写证据，保留原有失败与新增失败的区别。

循环执行剩余任务、相称检查、修复和保存检查点。task/todo UI 随进度更新；中断恢复核对文档、文件和实际进程，不靠上次会话的“完成”声明。发现改变已批准承诺的重大问题，或同一错误经有限尝试仍不能继续时，记录证据及可选处置再询问；不要为常规实现选择反复提问。提交按项目和用户已给授权进行。

## review：统一审查与验证

按 [审查规程](review.md) 提示范围、串行/并行方式及可用审查者；用户只记 review，不必记范围子命令。默认本 feature/bug fix 的累计修改，用户可指定全项目或自定义范围；文档阶段以文档为目标，实现后对照有效文档审查代码和测试。用 [调度接口](review-runs.md) 固定输入和登记有界轮次，必要独立记录按真实来源导入。

先执行或复用适用的确定性检查，再实际审查；获准修复后重验受影响部分并在预算内复核。最终分别报告检查和审查结论。已接入完整检查的事项运行完整 `tao verify <CHG-ID>`，缺策略、工具、有效证据或必需审查时说明未完成，不用局部通过代替交付。verify 保留为底层 CLI，不要求用户额外调用一个动作。

## debug、status、handoff、docs、finish

- **debug**：可独立处理缺陷或服务于当前实现。先只读调查现场和复现条件，用可证伪假设定位原因；需要写复现、测试或补丁时确认范围。实现阶段已有授权覆盖的调试直接进行。修复后重跑原场景及相关回归；若改变业务承诺，转入 refine。单纯定位请求不自动授权修改。
- **status**：只读展示阶段、实际任务、过期批准、已有检查/审查状态及下一步；不执行验证、修改任务或自动恢复。工具无法唯一选中事项时请用户选择。
- **handoff**：按 handoff 模板保存目标、决定、实际状态、证据、阻断及下一步的简短交接。展示链接、实际 worktree/branch 和可粘贴的 continue 输入。保留文件，不自动提交、停止会话或传送源码；恢复规则见状态接口。
- **docs**：在构建输出的写入授权内运行 `tao docs build`，实际检查生成入口并给出本地 HTML 链接。缺少书入口时先说明要创建哪些导航文件并取得确认。构建不包含部署。
- **finish**：核对交付检查与审查、运行中操作和未提交文件。按用户选择保留分支、合入目标分支、推送、删除 worktree/分支；展示具体对象及未提交修改，已有明确授权不重复问。只清理本事项拥有且已确认可删除的内容，不能使用强制删除掩盖未保存工作。必要经验写回既有权威文档，不为每次开发生成重复总结。报告完成/未完成事项与产物入口。

hook 仅在项目已配置时提供有界的文档写后反馈，不能替代阶段批准、自动推进用户检查点或启动长任务。shell 产生的修改未必触发文件 hook，agent 仍需显式检查。可复用的结果要说明原执行与当前适用性；保存规范统一见 [证据规程](evidence-retention.md)。
