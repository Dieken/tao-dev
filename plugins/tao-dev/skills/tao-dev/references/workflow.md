# 流程操作与工具调用

在进入需求、计划、实现、调试、恢复、验证或收尾工作时读取本规程。工程判断遵循同包的 [工程规程](engineering.md)；按项目现有语言、目录、工具和已作决定执行。用户通常只表达意图，agent 负责调用与必要参数，不要求用户逐次选择检查类型、范围或级别。

## 先判断可用能力

**当前版本没有 tao CLI。** 下表是后续工具接入契约；当前按“实际动作”执行，并说明尚无自动检查。不要执行不存在的命令，不寻找或安装 PATH 中碰巧同名的程序，不将人工查看冒充自动校验。

后续包提供 `scripts/tao.py` 或项目明确指定 tao-dev 入口后，才通过该受信任路径调用 `doctor --format json`。确认工具标识、协议版本和操作能力；特别区分 verify 的文档、项目行为与证据子能力。表中的 `tao` 是该入口的简写，不要求全局安装。入口或能力缺失时报告缺口，继续能完成的部分，必要保证缺失时保留未验证。

## 按任务阶段执行

流程名称采用 specify、plan、implement、review、verify。澄清属于需求工作，设计与任务拆分属于规划；这些是帮助理解的操作名称，不是每次都要启动的五个命令，也不要求分别生成文件。

| 时机 | 实际动作与最小产物 | 工具接入点，能力存在后才调用 |
|---|---|---|
| 首次进入项目或工具／配置变化 | 确定根目录、已有约定、当前目标及检查能力 | `tao doctor`；配置和能力未变时不反复检测 |
| specify：整理需求 | 复用已知目标与场景，独立分析用户建议，明确范围与验收；已有计划可继续使用 | 需要新计划时 `tao new change <slug>`；语言取项目约定，不重复追问；新增正式条目由生成器或 `tao id new` 分配 ID |
| plan：设计与拆分任务 | 检查实现与调用方，比较最小方案，明确依赖、修改范围和验证办法 | 文档修改后 `tao verify --only docs`；查定义用 `tao show <ID>`；工具不替 agent 完成设计 |
| implement：实现或重构 | 完成一个可验证结果，保护不相关工作，同步受影响规格与说明 | 文档变化用 docs 子集，行为变化用 `tao verify --only code` 或项目原生检查；读取局部结果，不声称整个变更完成 |
| 调试 | 保存现场、提出可证伪假设，以最小实验区分原因；修复后重跑原场景与回归 | 用已配置的 code 子集或项目命令执行；不以反复重跑至偶然成功掩盖失败 |
| review：审查 | 读取 [审查规程](review.md)，按风险对相关产物独立审查，加强审查优先跨供应商 | `tao status` 查已有证据时效，必要时调用相关 verify 子集；不虚构自动审查或跨模型执行结果 |
| 恢复会话 | 核实当前目标、决定、阻碍、文件状态与证据，不仅信任交接摘要 | `tao status` 与必要的 `tao show`；绑定已明确的目标，不重新让用户选择 |
| 中断或交接前 | 保存目标、约束、决定、实际状态、证据入口、阻碍和下一步 | 支持时 `tao context save --from <file>`；否则更新项目既有交接位置，不保存整段会话 |
| verify：交付前 | 核对验收、必需检查、任务与依赖、审查、证据及真实授权，说明结果与限制 | 执行不带 `--only` 的 `tao verify` 并读取完整报告；无单独收尾命令，不自动提交、合入或发布 |
| 删除条目或构建书籍 | 处理引用与退役；实际检查生成链接 | 分别使用支持的 `tao retire`、`tao docs build`，保持写入范围；构建不附带部署 |

局部文案／格式修正采用相称检查和交付说明，无需新建变更档案。沿用已有文档契约，不强制使用方迁移。实际没有必要行为检查时应有明确适用性依据；不能仅因修改的是 Markdown，就跳过 prompt、配置或操作说明可能影响的行为。

## 自动选择，必要时才覆盖

当前变更由显式 ID、变更目录、当前任务绑定或唯一活动变更确定；只有存在实际歧义时才询问。完整 verify 按项目已确定的策略选择文档、代码与证据检查。配置一次后不反复让用户选 profile；发现新风险则明确增加所需检查，不暗中降低门槛。

编辑期间可以用 `--only docs`、`--only code` 或 `--only evidence`，它们只给局部反馈，不替代交付前的完整调用。`--scope changed` 仍包含必要依赖和全局一致性检查；基线或影响不明时扩大到 all。预算不足或必要工具缺失时如实记录，不靠局部模式绕过。

对副作用或检查选择有疑问时用支持的 `--dry-run` 查看计划；它不执行验证，不构成证据。hook 实现后可做预算内的 docs 子集检查；完整验证由 skill 在交付前触发，无需用户再运行额外的收尾命令。重复事件和相同输入的检查应合并，必要的旧证据复用以完整指纹及有效期为依据。

## 读懂结果并保持边界

tao 退出 `0` 表示本次所选检查通过，`1` 表示条件不满足，`2` 表示配置／工具故障、能力缺失或检查未完成。`--only` 的 0 只对应 `coverage: partial` 和 `readiness: not-evaluated`；dry-run 的 0 仅表示计划有效。整体完成依据必须来自完整调用的 `coverage: complete`、`readiness: checks-satisfied`，再结合实际语义审查和授权。工具条件满足不代表语义正确、风险已获批准或已经发布。

项目原生命令按其真实退出码和输出解释，不能套用 tao 的退出码约定。逐项区分通过、失败、未执行、不适用和已过期；复用结果标记 reused 并给出证据入口，不用代码量、任务勾选或模型复述代替证据。

受检输入在验证期间或之后变化时重验受影响部分。内容指纹与必要环境是依据，VCS 修订只作补充。临时报告默认不是长期证据，需要长期引用时归档摘要与必要原报告，记录校验和及保存期限。

CLI、斜杠命令和 hook 只报告实际支持与执行的能力。测试本 skill 时仅在隔离项目或单次调用内启用，不全局安装、不修改全局配置；必要能力缺失时报告限制，不能伪装整体通过。
