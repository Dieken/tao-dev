# Agent 内开发流程

本页维护用户动作、阶段与授权；CLI 定位见 [工具规程](tools.md)，阶段记录见 [工作流状态](workflow-state.md)。

## 入口与授权

通过当前客户端的 skill 入口加载 tao-dev，按用户请求和项目状态选择动作；动作也可用自然语言表达。加载后无需重复动作名；目标明确时简短说明动作，纯讨论保持讨论。

先判断开发事项（CHG）归属：当前事项内调整走 refine，独立目标及已完成事项的后续需求走 new。已有规格但新增独立需求没有当前事项时，仍走 new 并复用该规格，只推进本次获准阶段。普通局部代码实现或修复可省略完整功能开发档案，但仍须在写入前读取 [工程规程](engineering.md)，修改后根据影响和风险安排检查，保留项目必需检查。用户已经给定单一检查方法，且不调用 tao CLI、不配置或解释检查策略时，直接执行该检查，不再读取工具或验证规程。普通局部文案／格式维护且无工作流职责时直接修改并检查受影响内容；不建立完整档案，也不把已开始的完整功能开发流程降级。

- 阶段写入需明确授权，展示实际新建、修订和复用文件。“同意，开始下一阶段”可同时批准当前产物与下一阶段写入。澄清完成、反馈意见、默认选项或无回答不构成写入批准。
- 完成文档及必要的格式、链接等检查后，展示产物和下一步建议。未明确获准进入下一阶段时暂停；文档完成、检查通过或用户认可内容，均不自动授权正式评审或实现。已有明确覆盖后续阶段的授权继续有效。
- 在批准范围内自主完成，只为重大范围／方案变化、必要人类决定或有限尝试仍未解除的阻断暂停。用户已明确要求的动作不再重复确认同一意图。

## 讨论与进度

先查项目事实与既有决定，只问影响当前目标、验收或重要取舍的未知。默认一次问一个关键问题，有依赖先问前置；独立且简单的问题可小批合问。优先使用当前模式可用的原生提问工具，不为此切换模式；不可用时用简短编号问题。决策选项给推荐理由、代价并保留自由输入；了解真实经历和需求时用开放问题，不用预设方案引导答案。

按阶段聚焦：spec 明确受益者、具体场景、现有做法、期望结果、范围与验收；design 比较可行方案、失败后果、持续成本和难撤销决定；plan／tasks 确定增量、依赖、验证及优先求证的风险。影响范围、外部行为或验收的选择须先确定，或由用户明确委托 AI 决定，不能暗含在任务中；普通技术细节自行决定。关键问题明确后即可结束本轮讨论，剩余可延后项注明处理时机；不重问已确认决定，不穷尽决策树。质疑双方判断的依据与方法见 [工程规程](engineering.md)，正式独立审查仍须在授权内启动。

阶段完成、暂停、交接及 continue 核对后，简述已完成、进行中、待办／阻断，推荐先做哪一步及理由，说明是否缺授权并链接产物。耗时的实现与测试使用可用的原生 task/todo 工具；没有时用“任务｜状态｜结果或阻断”表格。任务完成、测试有结果，或阻断情况、计划发生变化时，更新进度，长操作期间简报已知进展；代码写完但验证未过不得标完成。表格无变化时，不必每次调用工具都重新展示；已有正式计划是持久依据，列表只是进度视图。

## setup：项目接入

按 [项目接入](project-setup.md) 探测工具、配置最小检查策略并执行获准基线。需要 tao 能力但缺配置时，可在已有写入授权内补齐，不要求先重装插件。

## new：需求到规格

1. 调查现有行为、规格与相似实现，澄清业务范围、场景和验收；路径、术语和文档语言按项目约定处理。
2. 汇总需求与未决点，确认澄清完成，并取得创建 worktree／编写 spec 的授权。意见未收敛时继续讨论。
3. 调用 workflow start，默认使用隔离 worktree；复用已有副本，记录根、分支与基准。前提和冲突处理见 [工作流状态](workflow-state.md)。
4. 在副本中编写或修订 spec，保存检查点、执行文档检查并展示链接，按上述授权规则继续或暂停。

正式文档采用 [文档规程](documents.md)。完整功能开发的 spec、design、plan 各有入口，优先复用；位置与拆分见 [文档组织](document-layout.md)。仅在编写 plan 时调用 `tao new --slug <原 slug> --change <CHG-ID>`，不提前生成空计划或未来阶段产物。

## continue：推进或恢复

按 [工作流状态](workflow-state.md) 的接续步骤核对并展示进度后，在已有授权内继续；continue 本身不扩大授权。缺授权时展示下一阶段范围与建议并暂停，意见在当前阶段修订。

| 阶段 | 工作 | 下一步 |
|---|---|---|
| spec | 业务范围、REQ／UC、可判定验收 | 查看／修改，或批准 design |
| design | 最小方案、接口、约束、失败与验证设计 | 查看／修改，或批准 plan |
| plan | 可验证 TASK、依赖、修改范围和检查办法 | 修改、文档审查或批准实现 |
| implement | 按批准任务实现与验证，更新进度 | review |
| review | 确定性检查与实际审查 | 修订／修复或 finish |
| finish | 按授权整理、集成与清理 | 报告实际结果 |

进入实现前，若当前版本既无文档审查结果也无跳过决定，提供先审查或跳过可选审查的选择并记录；项目必需审查不可跳过，已有有效结果或决定不重复询问。

## refine：修订已有内容

定位受影响的 spec、design、plan 及下游工作；按授权更新。业务范围变化同步规格、设计与任务，技术方案变化同步设计与计划，纯任务拆分只改安排。用 workflow revise 撤销相应下游批准，保留代码和稳定 ID。正式删除走 [退役规程](retirement.md)。展示差异与检查点，修订本身不自动授权实现。

## implement：完成批准计划

显式 implement 在计划明确且前置条件满足时即授权该计划的实现与测试；前置文档阶段或审查选择未完成时回到对应检查点。按依赖完成小增量、检查受影响行为并修复，依据真实结果勾选任务并保存检查点；测试与工程取舍见 [工程规程](engineering.md)，结果保存见 [证据保存](evidence-retention.md)。提交遵循项目与用户授权。

## review：审查与验证

按 [审查规程](review.md) 确定范围、方式与预算，使用 [审查调度](review-runs.md) 固定输入和记录轮次。文档阶段审查文档，实现后对照有效文档审查代码与测试。检查、发现和处置分别报告，通过后进入 finish。

## 其他动作

- **debug**：先调查与复现，再按 [工程规程](engineering.md) 定位原因。定位请求不授权补丁；已有实现授权覆盖时直接调试、修复和回归，业务承诺变化转 refine。
- **status**：只读展示阶段、任务、批准和证据时效及下一步，不运行验证或自动恢复；事项仍不明确时请用户选择。
- **handoff**：按 [工作流状态](workflow-state.md) 和 handoff 模板保存恢复摘要，并展示其返回的入口。
- **docs**：显式调用授权常规本地构建输出，按 [出版规程](publication.md) 构建并检查 HTML。缺书入口时展示拟建导航并确认，构建不含部署。
- **finish**：核对交付检查、审查、运行中操作与未提交文件；按已确认对象执行保留、合入、推送和 worktree／branch 清理。只删除本事项拥有且已确认可删的内容，不强制丢弃未保存工作。按 [工程规程](engineering.md) 沉淀有用知识，报告完成和未完成事项。
