# 项目接入

处理用户的 setup 动作时读取。它接入业务项目；安装 tao-dev 仍使用 install，底层 `tao setup` 只准备 tao 自身运行环境。

1. 运行 `tao --project <root> project inspect`，读取返回的 manifest、CI、已有检查配置，并查看相关源码。探测不会运行候选命令或安装软件。可识别 Python、JavaScript、Rust、Go 和 Make 的常见入口；子目录也会探测，排除依赖、worktree 和生成目录。扫描限制或解析失败会报告覆盖缺口。未识别的技术栈由 agent 依据项目实际文件调查，不假称工具已经识别。
2. 区分项目已声明的工具、当前可运行的工具和实际通过的检查。executable_available 只表示能找到命令入口，不证明其插件或包已安装；candidates 是待核对命令，不直接写成通过证据。已有 CI 和项目命令优先于探测建议；检查是否有 watch 模式、外部服务或写入副作用。
3. 非空且技术栈可确定时，说明已有测试、类型检查、静态分析、依赖扫描及构建入口；只推荐能填补实际缺口的工具，解释用途和维护代价。空项目不预装工具，技术方案明确后重新 setup。通过客户端原生提问工具让用户选择“接入现有工具”“同时补充选中的工具”或“仅查看建议”。已有授权覆盖这些动作时不重复询问。
4. 在用户确认范围内，使用项目自己的依赖管理器与锁文件准备工具，不安装到 tao 的运行 venv。不自动全局安装、不新增 CI 平台、不降低已有门槛。把选中的命令按 [验证规程](verification.md) 接入；参数数组来自已核对的项目入口，不能拼接用户自然语言。
5. 创建最小 TOML 草稿到项目临时目录，明确文档管理范围、项目语言和必要检查。已有文档只逐步纳入，不把全部 Markdown 强行转换为 tao 格式。空项目尚无受管理文件时可配置 include=[]；这不代表文档检查通过。
6. 用 `tao project configure --from <草稿相对路径>` 应用；已有配置先读取完整内容，保留原有约定，并传 `--expect <inspect 返回的 config_digest>`。工具先验证配置和检查策略，拒绝过期覆盖；配置语义未变时保留原文件，不重复改写。该命令本身不安装依赖、不执行检查。
7. 根据已批准方案核对生成目录与 `/.worktrees/` 的忽略规则；`.tao/config.toml`、工作流状态及正式 handoff 不当作缓存忽略。运行 doctor 和获准的基线检查，报告实际写入、已运行与未运行项目，并提示 new 或 continue。重复 setup 检查和补充，不重置配置。

setup 是可选的：用户可直接 new；需要 tao 配置才能提供的 hook 或完整检查时，由 agent 说明缺口并在相应写入授权内补齐。不能因为用户未先执行 setup 就要求重走安装流程。
