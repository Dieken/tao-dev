# 审查方法

review doc 与 review code 都是 skill 动作。审查支持判断，不是注册、审批或交付认证系统。

## 范围与强度

局部低风险改动可自查；普通跨模块工作优先独立上下文审查；数据完整性、权限和难恢复迁移等高风险改动优先不同模型或供应商。按实际可用能力与用户限制选择，不因角色名不同宣称模型独立。能力不可用时说明未执行，不能伪造通过。

## 方法

1. 固定实际受检范围和版本，提供原始目标、有效约束、产物及相关调用方和测试。没有可还原快照时说明限制。
2. 独立审查者先看材料，不先看作者自评或其他审查意见；必要的正式决定和理由仍完整提供。
3. 文档检查需求验收、设计假设、边界、成本及任务覆盖；代码追踪触发条件、失败路径、调用方、数据与安全约束。也寻找无需求支撑的复杂度，允许无发现。
4. 每项发现说明定位、违反的契约、触发条件、依据、影响及最小修复或求证方法；区分真实缺陷、未证实风险和非阻断建议。
5. 作者逐项核实，以契约、可复现事实或测试裁决，记录采用、不采用或未解决的理由。模型一致不是证据。修改后按影响复核，不为凑轮数反复审查。

## 保存与下一步

不创建审查批次、调度记录、回执或强制报告。详细输出留对话或临时目录，计划只保留当前范围、结论、限制与下一步；长期要求和决定直接更新 spec/design/ADR。明确需要独立长期引用时才使用 [可选报告写法](review-reports.md)。审查结束推荐修复/refine、implement、针对性复核或汇报当前成果；不以任务全勾选推断已审查。
