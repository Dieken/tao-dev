# 正文写法

编写或审查规格、设计、计划正文时读取对应小节及片段模板。共同元数据、ID 和文档检查见 [文档规程](documents.md)；精确字段与允许位置以 [格式注册表](../assets/document-profiles.json) 为准。

questions 只写尚未确定的目标、范围、方案或验收条件；没有则省略或写“无”。确需延后的需求说明原因与后续承接，不能静默缩小范围。已知范围归 scope，验证结果及缺口归 verification，后续工作归 tasks；按实际内容组织章节，不制造审批字段或豁免门禁。

## 条目的共同语法

正式条目使用文档顶层的三反引号 MyST 块，类型为 req、uc、adr；选项后空一行再写正文，不嵌入列表、引用或其他条目。选项、状态取值与关系目标类型见注册表的 `entities` 节；关系值是逗号分隔的完整 ID，不含空项或重复项。superseded 对象须有另一条目的 supersedes 指向它。

字段用 `<!-- tao:field key -->` 标记，每个适用字段为非空 Markdown 段落，保留稳定键而不强制顺序；标记在代码或引用中不生效。多个独立承诺拆成条目，通过 ID 关联，不复制验收标准。

## REQ：系统承诺

使用 [REQ 片段](../assets/templates/req-block.md)，在 spec.requirements 定义；每份规格至少一个 REQ。正文采用 EARS 条件化表达，每个 REQ 对应可独立接受、修改或失败的一个承诺：

| 条件 | 中文写法 | 英文关键词 |
|---|---|---|
| 始终适用 | 系统应…… | shall |
| 事件触发 | 当……时，系统应…… | When |
| 状态持续 | 在……期间，系统应…… | While |
| 产品包含某功能 | 对于包含……功能的版本，系统应…… | Where |
| 异常发生 | 如果……，则系统应…… | If / then |
| 组合条件 | 按适用条件、状态、触发、响应组织 | 组合上述关键词 |

例如：当用户取消导出时，导出器应停止该次导出。只选适用条件，不为填满类型添加需求。

- REQ_BODY：系统主体、条件与可观察响应。验收必要的时间、容量、精度须有单位与测量条件；未知数值留作未决项。
- REQ_ACCEPTANCE：验证输入、观察方法和通过判据，或引用 UC；不重复正文或增加承诺。
- REQ_SOURCE：真实来源与必要动机，关联具体受益场景；不以指定技术替代需求依据。

范围、术语和设计理由不套 EARS。公式、状态机或决策表更清楚时引用其权威定义及判定办法；用户故事可解释动机，不能代替系统承诺。

## UC：场景与性质

使用 [UC 片段](../assets/templates/uc-block.md)，位于 cases 或 invariants；用户明确合并文档时也可位于 plan.design。

- UC_GIVEN：初始条件、输入域和约束。
- UC_WHEN：触发动作或操作序列。
- UC_THEN：可观察、可断言的结果；性质说明适用输入范围和谓词。
- verifies：关联被验证的 REQ。

项目已有可执行 Gherkin 场景时引用其位置和关联 ID，不复制步骤。MyST UC 本身不是可执行测试；随机试验通过不等于形式化证明。

## ADR：选择与后果

使用 [ADR 片段](../assets/templates/adr-block.md)，位于 decisions、design 或 architecture。长期决定的抽取条件见 [文档组织](document-layout.md)。

- ADR_CONTEXT：问题、约束和实际备选。
- ADR_DECISION：选择与理由。
- ADR_CONSEQUENCES：收益、代价、限制与后续责任。

字段内容说明真实背景、决定与后果；可以使用加粗标签帮助阅读，但不强制粗体或标点形式。显示标签可翻译，结构键保持不变。

## 设计内容

设计按需要说明边界与架构、接口与数据、不变量、失败处理和验证，不强制无关章节。需要长期复用的设计独立维护，plan 引用适用设计；局部变更可复用现有设计或在计划说明差异，不为每项任务新增设计文档。具体组织见 [文档组织](document-layout.md)。不复制整段代码充当设计。

明确系统边界与数据流、公开接口和调用方、数据约束和所有者、状态转换、失败后的状态与恢复。重要取舍记录可行备选、理由和代价，已有 ADR 则引用；只记录影响决定的签名、模型、公式或图，详细实现由代码承担。已有基线时说明保持哪些可观察行为，避免把“优化”默认解释为允许语义变化。

比较简单可行替代与持续维护成本，不因表面相似引入抽象，不以既有投入替代必要性。说明知识归属和公开契约；新增依赖、服务或恢复机制须有具体收益和适用条件。涉及并发、多步操作或权限时，写清数据所有者、原子性、信任边界及失败后的状态；重试须说明幂等或去重依据与边界。安全或迁移设计按实际资产、数据和消费者说明约束，不用口号代替可检查条件。

verification 说明检查什么、输入与环境、比较基线、执行办法、通过条件及必要报告；正确性性质关联 UC，具体任务关联 REQ／CHG。按风险说明每条需求的验收在哪一层核对，不套统一测试次数或覆盖率。断言来自需求、独立算例或性质；替身可隔离非目标依赖，不能替代关键集成的证据。必要验证不能写成可选，不适用须说明条件依据。项目检查直接调用原生入口，不复制到 tao 配置，不因创建文档自动执行；结果解释见 [确定性检查](verification.md)。

若形式化模型有助于判断重要设计假设，文档说明待检查规则、模型边界、反例判据及与真实系统的对应关系；不默认要求建模或指定工具。已有类型约束、性质或常规测试足够时不增加模型。模型“未发现反例”仅对声明的规则、边界、版本和配置成立，不等于完整证明、实现符合模型或验收通过。反例须区分模型错误和真实契约缺陷；重要结论未确定时，计划表达依赖而不是虚写确定结论。

性能与成本承诺需说明工作负载、规模、基线版本、环境、测量办法、重复次数或统计方法、阈值与容差。设计估算与实测数据明确区分；没有实测就保留待验证，不能把公式推导出的预期节省写成已达成收益。

## 任务与证据

正式 TASK 仅位于 tasks 章节，每项为扁平 checkbox 和固定字段；分组可用三级标题，不能再维护一份父任务完成状态：

```markdown
- [ ] `TASK_<YYYYMMDD>_<16位随机串>` 可验证的结果
  - relates: ["REQ_<YYYYMMDD>_<16位随机串>"]
  - verify: 实际检查办法及预期结果。
```

字段编码和允许的引用类型见注册表的 `tasks` 节。字段行缩进两个空格；relates、depends_on 与 evidence 可选，提供关系时不含重复成员且依赖不得成环。没有依赖时省略 depends_on；所属事项由 plan/tasks 的 change 表达，不要求每项任务重复关联同一 CHG。verify 为非空单行文本，写实际检查办法与预期结果，不能仅写“完成某模块”。影响需求或方案的未知先安排求证，下游实现依赖真实结论。

evidence 不是勾选完成的必需条件；任务勾选仅表达所述工作结果完成，不证明已验证、已审查或已交付。已有有价值的证据链接可保留，不另维护父任务状态或客户端持久进度副本。项目结果与临时执行步骤的区别、读取与回写规则见 [持久计划](planning.md)。

plan 的 verification 先写检查办法，执行后覆盖更新当前结果摘要；用章节键定位，不另维护成对 results 标记。相同范围的进度合并，不按任务或重试追加流水账；独立范围的历史结果注明版本与限制。输入引用和长期独立摘要见 [证据保存](evidence-retention.md)。

独立 evidence 的字段、结果与时间语义见 [证据保存](evidence-retention.md)。

## 内容审查

检查条件类型、系统主体、响应可观察性、独立承诺拆分，以及验收是否改变原需求。中文不要求英文关键词；句式匹配不能证明语义正确。当前没有 EARS 语义检查器，结构检查与实际验收分别报告。
