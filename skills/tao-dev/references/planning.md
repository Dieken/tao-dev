# 持久计划与项目进度

需要跨会话、多人协作或明确跟踪结果时使用计划与任务文档；局部小改动复用已有文档，不为形式齐全新增计划。计划描述一次事项的目标、依据、可验证结果和当前实际进度，不是强制开发阶段表。精确编码见 [注册表](../assets/document-profiles.json)、[正文写法](document-content.md) 与 [计划模板](../assets/templates/plan.md)。

## 记录目标与任务

先查找当前项目的相关计划，能覆盖同一事项就更新原对象，不重复创建。按实际需要记录目标、范围、依据和任务；已有规格和设计用 `spec_docs`／`design_docs` 或正文链接引用。必要的局部取舍可留在计划，不复制长期正文。

正式 TASK 描述可核对的结果，而不是“读取文件”“调用工具”等临时步骤。每项 `verify` 说明检查办法与预期结果；`relates` 表达相关需求或其他事项，`depends_on` 表达真实依赖，不能用排列顺序代替。所属事项由计划和任务集的 `change` 表达。影响目标、方案或验收的重要未决问题，应记录需要求证的结果及其依赖。

默认在 `plan.tasks` 内维护唯一任务集。确因规模或并行编辑需要拆分时，用 `tasks_doc` 唯一关联一份 [任务附件](../assets/templates/tasks.md)，附件与计划共享 CHG，移除原内联任务集，不复制复选框或另设父任务完成状态。对象移动和修订保留 DOC/CHG/TASK ID；只有新增独立对象才分配新 ID。

## 读取与核对

以用户指定目标或已明确的计划为起点，用 [status 查询](tools.md#查询与进度) 定位计划，读取唯一任务集及相关权威文档，再核对当前文件、实际产物和可用结果。多个候选无法区分时列出候选，不按修改时间猜测；任务集缺失、错绑或损坏时先说明材料问题。临时摘要与客户端任务只能辅助定位，不替代仓库计划。

读取验证摘要（`verification`）时核对结论的范围、版本与当前事实。发现冲突时说明依据，修正过时任务状态、结果摘要或权威知识；不能自动信任旧勾选，也不能机械改规格去迎合实现缺陷。并发编辑产生的范围、决定或结果冲突须明确解决，不能以最后写入者覆盖进度。

## 回写实际结果

有实际结果后及时更新唯一任务集和计划摘要。客户端临时步骤不形成第二份项目进度，不能把其完成数当成项目完成数。

尚未完成或受阻的任务保留未勾选，在计划正文说明剩余结果、阻塞原因和解除条件；不要另造复选框状态或把等待写成完成。跨会话需要的关键决定和依赖也须记入仓库文档，不能只留在客户端任务备注。

任务勾选仅记录所述工作结果已完成，不证明检查通过、独立审查完成或交付获认可。`verify` 保留判定方法，实际观察和限制归 `plan.verification`，不能把预期结果写成观察结果；证据链接的处理见下节。

## 结果保存

计划的 `verification` 章节合并同一范围的当前摘要，不追加操作流水账。记录受检范围与版本、实际执行时间、命令或观察方法、结果、未运行／未覆盖项及剩余限制；未知写明未知。分别记录 [文档校验](tools.md#文档校验)、项目检查和 [语义审查](review.md) 的结果，审查注明实际审查者、对象和结论。

历史失败不能改写成成功，旧版本通过不能证明当前输入通过；文档编辑时间或 ID 分配日不能代替实际观察时间。临时日志消失不改变已经发生的结果或任务完成状态，但不能再声称原始材料可查。

审查与证据详情、命令日志、截图、输入清单与本地生成的文档放在配置的 `temporary`（默认 `tmp/tao`）或 CI 产物中，不注册正式对象，也不纳入文档书籍。核实后的持久结论、约束和原因合并到权威文档，保留必要的来源链接、适用范围与限制。专项原始材料留存由项目或外部系统负责。

`TASK.evidence` 是普通 Markdown 链接，可指向计划验证章节或检查产物；链接及原始材料是否可用，与任务是否完成分别判断。没有独立证据文件不影响任务完成的判定。

用户要求临时总结时直接提供普通 Markdown 或对话摘要，不注册 ID、不纳入文档书籍，也不能替代计划回写。临时材料缺失不妨碍读取仓库中的计划和事实。

## 完成后的知识归属

完成的计划保留为本次变更记录，不持续充当项目当前状态说明。将可复用的承诺、实际边界、长期取舍及操作限制更新到规格、设计、ADR、指南或运维手册；计划链接这些权威位置并保留当时范围与结果。保留原 ID 和有价值的引用，任务完成不自动退役文档，也不将文档 `status` 自动设为 `accepted`。后续独立事项使用新计划，长期文档继续维护当前事实。
