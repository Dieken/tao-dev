# 在 agent 会话中完成开发

<!-- tao:section scope -->
## 适用范围

本指南展示一次完整功能开发，以及修订、调试、审查、交接和恢复。安装见 [README](../../README.md)；安装完成后的操作都在 coding agent 会话内进行。后面的完整周期示例以 tao-dev 自身为开发对象，需求是给文档增加持续本地预览。它不是当前已经实现的 `tao docs serve` 用法。

用户决定业务目标、重要取舍与写入范围；agent 调查工程细节，选择文档位置和语言，调用 tao CLI 与项目工具。每个阶段开始写文件前确认范围；清楚的“批准当前产物并开始下一阶段”可以一次完成确认，已有覆盖后续工作的授权不重复询问。

<!-- tao:section prerequisites -->
## 开始之前

完成 tao-dev 完整插件安装或 [独立 skill 接入](clients.md)，在目标项目打开新会话。完整功能开发流程使用 Git，需要已有初始提交；默认 worktree 位于项目根 `.worktrees/`。agent 会检查未提交修改、忽略规则和路径冲突，已有隔离 worktree 可复用。基础文档检查仍可用于没有 Git 的目录；其他版本管理工具尚未提供完整流程适配。

首次加载：Claude Code 用 `/tao-<动作>`，Codex 用 `$tao-dev <动作>`，其他客户端使用原生 skill 入口。下面示例在 tao-dev 已加载后统一使用自然语言。每段示例都是一条消息：**阶段之间分开发送；有补充要求时，与动作写在同一条消息里**。动作本身已表达操作意图，无需附加同义说明。后续批准和讨论可直接使用自然语言。客户端提供原生提问选择或 task/todo 列表时优先使用；不可用时显示简短编号选项和任务摘要。默认选项、超时、未回复都不代表批准。

## 完整开发示例

### 自然语言与已有文档

下面以一个已有导出功能的项目为例。明确动作是可靠入口；tao-dev 已加载后，也可以直接发送下面的一条消息：

```text
希望导出支持 CSV。先讨论需求，不要写文件。
```

agent 会先调查和澄清。独立新目标建立新开发事项，但已有导出规格和设计可以复用或修订；只补缺失文档，任务默认内嵌本次计划。已完成的旧计划保留历史，不追加新任务。

当前事项内的调整可以直接说：

```text
把刚才的批量操作取消，只支持单条。修订受影响的文档，先不要进入实现。
```

agent 会按 refine 处理，说明受影响的规格、设计和任务，保留 ID，重新检查下游批准。若无法判断是调整当前事项还是另开事项，会提供相应选择及推荐理由；不会让你先记住动作分类。是否写文件仍按阶段授权，不因动作识别自动批准。

没有显式指定 skill 时，是否自动加载取决于客户端配置和选择机制；tao-dev 不承诺监听每条消息。未进入预期流程时，使用上面的显式动作入口。

### 1. 可选：接入项目检查

```text
请接入当前项目的检查工具。
```

agent 先探测已有技术栈、依赖声明、测试、静态检查、CI 和 `.tao/config.toml`，区分“已声明”“可运行”和“实际检查通过”。内置探测识别常见 Python、JavaScript、Rust、Go、Make 入口；未知技术栈由 agent 继续调查，扫描不完整时说明范围。

非空项目才针对确定的技术栈建议补充工具。你可选择仅接入现有检查、同时补充选中的工具，或仅查看建议。例如回复：

```text
只接入现有检查，同意写入最小项目配置并运行这些检查。
```

agent 保留已有配置，在批准范围内生成或更新 `.tao/config.toml`，核对生成目录及 `.worktrees/` 的忽略规则，运行 `tao doctor` 和约定基线。补充工具使用项目自己的依赖环境，不装进 tao 的 venv。空项目不猜技术栈、不预装工具。重复 `setup` 动作用于检查和补充，不重置项目。

这里的 `setup` 是 agent 动作，接入业务项目；终端里的 `tao env prepare` 只准备 tao 自身运行环境。你无需另外执行 shell 命令。也可直接使用 `new` 动作，缺少必要配置时 agent 会解释并按已有授权补齐。

### 2. 提业务需求并澄清

```text
请开始新的开发事项： 我想在本机预览 tao-dev 的文档，修改文档后自动更新预览，停止预览后不留下后台进程。
```

agent 查看当前 HTML 构建能力，询问真正影响范围的问题，例如是否仅限本机、构建失败时显示什么、是否自动打开浏览器。你只需回答业务选择，不必提供工程规范、文件名、slug 或文档语言。例如：

```text
只允许本机访问；不自动打开浏览器，显示可点击的地址即可；构建失败时显示错误并保留上一次成功的预览。
```

讨论收敛后，agent 总结需求，询问澄清是否结束以及能否写文件。确认后再回复：

```text
需求已澄清，同意创建 feature branch 和 worktree，并开始编写 spec。
```

agent 创建或复用隔离 worktree，记录分支起点，在其中创建或更新适用 spec。返回实际 worktree、分支、spec 链接、检查结果及下一步。此时不会一次写完设计、计划和代码。

### 3. 查看并完善 spec

打开 agent 给出的 spec 链接。需要修改时直接给意见：

```text
请补充：端口被占用时应明确报错，并提供重新选择端口的办法。先修改 spec。
```

agent 留在本阶段修订并再次展示。确认后：

```text
spec 符合预期，同意开始编写 design。
```

这条消息同时批准当前规格和下一阶段的文档写入。单纯“我看到了”或提出意见不会推进阶段。

### 4. 查看 design，再进入 plan/tasks

agent 比较简单可行方案，说明接口、数据与进程归属、失败处理、测试方式；返回独立 design 入口。已有适用的共享设计可以直接更新或引用，避免重复维护。

```text
design 符合预期，同意开始编写 plan 和 tasks。
```

agent 生成实施计划、可验证任务及依赖，关联规格与设计。spec、design、plan 在完整流程中各有明确入口；小需求通过简短内容控制成本，默认不把 design 隐藏在 plan 内。tasks 默认内嵌 plan，规模较大时再拆分。计划中的设计部分引用设计文档。

### 5. 细化计划或审查文档

计划可反复扩展、细化、删减。

```text
请先做手动刷新可用的最小版本，把自动刷新拆成后续任务；同步需要调整的规格、设计和计划。
```

agent 先说明影响，再在已授权范围内修订。任务和文档稳定 ID 保留；取消正式条目时展示退役及引用影响，使用底层 retire 处理，用户无需记住另一个动作。旧的下游批准失效时会明确显示，已有代码不会被自动丢弃。

spec、design、plan 任一阶段均可发起文档审查。

```text
请审查当前文档是否一致、可实现、可验收。
```

review 首先展示实际范围、审查方式、预计轮次和预算，请你确认。未做过文档审查时，进入实现前会询问是否先审查；可跳过的是可选审查，项目规定的必需审查不能跳过。已审查当前版本后不重复问。

### 6. 批准实现，自动完成任务

```text
同意按当前计划开始实现。
```

当前计划明确且前置检查已满足时，implement 本身就是按该计划开始实现和测试的确认，无需再回复“同意实现”。agent 完成代码、单元及必要集成测试，运行适用检查，修复失败，更新实际任务和证据。实现阶段尽量自动推进，不为常规实现选择反复提问；重大范围或方案变化、必须由你决定的问题、有限重试仍无法解决的阻断才暂停。长时间运行本身不使批准失效；勾选任务和追加验证结果不会使原计划批准失效。

每个阶段结束都显示已完成、待做、阻断和下一步；原生 task/todo UI 映射实际任务，持久任务仍以文档为准。提交是否自动进行遵循你和项目已有的授权。

### 7. 统一审查实现与检查结果

```text
请审查当前事项。
```

默认范围是本 feature/bug fix 从记录的分支起点以来的累计修改，包含多次提交、暂存、未暂存和未忽略的新文件；不是仅最后一个 commit。agent 展示范围后请你确认，也可在同一动作里要求“对照全部文档审查整个项目”，或指定文件。分支经过 rebase 导致旧基准不再适用时先确定新的比较依据，不猜起点。

| 方式 | 建议与取舍 |
|---|---|
| 单个独立审查者 | 小修复推荐；调用与汇总成本低，检查各方面需要依次完成 |
| 并行独立审查 | 常规 feature 通常推荐两个，分别关注需求/测试和实现质量；反馈更快、角度更广，但调用及汇总成本更高，需核对交叉影响 |

默认最多三个并行审查者。先核对客户端真实能力；未提供 subagent 时不假称已派生。第三方模型或 coding CLI 只有在实际可用、数据发送和费用已有授权时才调用，不为审查自动安装、登录或更改全局配置。不同会话或 CLI 不自动代表不同模型或供应商。

审查默认一轮独立初审加最多一轮定向复核，总调度时间预算默认为 1,800 秒；可以在开始前明确调整。失败尝试同样占用轮次，中断恢复不重置预算。耗尽后仍有阻断会展示证据与选择，不无限“审到同意”。该预算只用于审查，不限制实现阶段的持续时间。

agent 先运行或复用适用确定性检查，再开展语义审查，汇总去重后的问题。你确认修复范围后，重新检查受影响部分，并在预算内复核。最后分别说明测试/静态检查结论、审查结论与未覆盖范围；底层 `tao verify` 负责汇总证据和必需条件，用户不再另发 verify 动作。

### 8. 构建 Sphinx book

```text
请构建当前项目的文档。
```

docs 本身就是本地构建请求，包含常规构建输出的写入，无需再回复“同意构建”。agent 定位已安装的 tao 启动器，执行底层 `tao docs build`，使用安装时准备的出版 venv 运行 Sphinx，检查实际输出并给出 HTML 入口。默认生成目录是 `tmp/tao/book/`，项目可配置。缺书籍导航时先说明需要创建哪些文件，再按授权补齐。构建本地文档不包含外部部署，也不等于示例中尚待开发的持续预览服务。

### 9. 选择收尾

```text
请整理收尾状态并列出待选择的操作。
```

agent 核对检查、审查、运行中操作和未提交文件，展示具体分支及 worktree，并让你选择保留、合入、推送或清理。例如可先要求：

```text
保留 feature branch 和 worktree，先列出合入主分支前还需要处理的事项。
```

你也可明确授权所需的合入、推送和清理。检查通过本身不会授权这些动作；未保存内容不会被强制删除。确有复用价值的经验写回已有权威文档，不为每次开发生成一份重复总结。

### 阅读文档关联

Sphinx 页面标题下的“关联文档”表显示关系、文档类型和当前标题，点击即可在规格、设计、计划之间追溯。计划内嵌任务链接到本页任务节；独立任务附件链接到任务文档。需求和任务依赖也显示可点击的类型与标题。标题或路径变化后，正式链接仍用稳定 ID 解析。

表格由文档关系生成，不需手工维护。它说明结构关联，不能证明设计满足需求或代码已经通过验收；阅读源码时，元数据保留正式 ID，正文可以使用可读标题说明。

## 中断、交接与排障

### 随时可用

| 用途 | 已加载 skill 后的消息 |
|---|---|
| 只读查看阶段、完成事项、阻断和下一步 | `status` |
| 核对实际状态并继续当前工作，也可在新会话恢复 | `continue` |
| 根据意见修订已有 spec、design、plan/tasks | `refine` |
| 调查缺陷、复现和定位，获准后修复 | `debug` |
| 保存交接摘要并给出新会话的继续输入 | `handoff` |

refine 的修改意见、debug 的故障现象可沿用上下文，也可随动作补充；缺少必要信息时 agent 会询问。

### 同一会话中继续

先说“请查看当前事项的状态”。status 只读，不运行测试或改写完成状态。继续工作：

```text
/tao-continue
```

或：

```text
$tao-dev continue
```

agent 核对当前阶段、实际文件、批准、任务、证据和正在运行的进程。已有批准范围内继续；缺少阶段批准时展示下一步并询问。不会因为一次中断重建分支、重做已完成任务或重复启动尚在运行的测试。

### 退出后，在新会话中恢复

在原项目或实际 worktree 打开新会话，发送相同的 continue 输入。多个工作并存时会请你选择，不按“最近修改”猜测。spec/design 阶段即使尚无 plan，也能使用 `.tao/workflows/` 的检查点恢复。已经丢失且未保存的讨论或批准无法凭文件推断，需要补充关键决定。

### 主动交接

```text
请保存当前事项的交接摘要。
```

agent 返回实际交接文件链接、worktree/分支，以及包含工作标识的可粘贴 continue 输入。新会话使用那条输入即可，不必手工拼接路径。handoff 是正式项目文档，默认随项目维护，不加入 `.gitignore`；`.tao/workflows/` 保存必要决定与恢复状态，也不是可随意丢弃的缓存。是否提交遵循已有授权。

continue 核对交接与当前实际状态，记录已协调的交接版本，保留文件；后续继续不会重放旧的“下一步”。交接内容更新后会重新识别。没有先做 handoff 仍可恢复已持久化的进度，交接不是恢复前提。

### 调查问题

```text
请调查当前故障： 文档构建失败后，预览页面一直没有更新。请先复现和定位原因，再说明修复范围。
```

debug 可独立调查或在实现中使用。定位请求不自动授权补丁；已有实现授权覆盖的调试则直接进行。修复后重跑原场景和相关回归，涉及业务承诺变化时回到 refine。

### 常见状态说明

- 找不到命令：查看安装摘要中的绝对入口，或重新运行原安装命令修复。安装器不会修改 PATH，正常 agent 流程不依赖你设置 PATH。
- hook 没有反馈：确认项目已有 `.tao/config.toml`、客户端插件与 hook 已启用。hook 只做短文档写后检查，不能推进阶段或代替完整验证；shell 写入也未必触发客户端文件事件。
- 检查过期或审查输入变化：agent 重验受影响范围，不把旧的通过当作当前结论。
- 审查预算耗尽：先处理已确认的阻断，再决定是否授权额外预算；重新 continue 不会清零轮次。
- 文档或状态被外部修改：先协调实际内容；旧批准不再适用时重新确认受影响的阶段，保留已经完成的工作。
