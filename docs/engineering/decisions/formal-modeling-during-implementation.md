# 保持自然语言需求，按风险在实施阶段建模

<!-- tao:section decisions -->
## 决策

```{adr} 保持自然语言需求，按风险在实施阶段建模
:id: ADR_20260927_NQCTSW9RG77YA2P4
:status: proposed
:links: REQ_20260914_4CS6P421MGW68PME, REQ_20260914_0J68SDKV86ENKER2

<!-- tao:field context -->
**背景与备选：** 本决定保留 tao-dev 自身的工程设计依据，不是分发 skill 的建模流程。REQ 需要供用户、agent 和实现者直接阅读，也要能表达行为、质量、约束和业务规则。一种做法是把 REQ 改成结构化 EARS 或 FRETish，并维护形式化词汇和时序公式；另一种做法是保留自然语言需求，只为可能推翻方案的重要问题安排可验证的建模成果。前一种做法增加语法、解析工具、术语映射和同步成本，仍不能消除业务术语、环境假设与模型范围的歧义。完全不考虑建模则可能错过在大量编码前发现并发、状态和对象关系问题的机会。

<!-- tao:field decision -->
**选择：** REQ body 保持自然语言；EARS 帮助作者写清主体、条件、响应和验收，不强制标准句式。不引入 FRETish、形式化 glossary 或自动需求形式化。维护本仓库时，按风险为重要不变量安排建模成果任务，并优先解决可能推翻方案的问题；它与类型检查、测试和实现使用相同的 TASK、依赖、验证和证据机制，不引入产品执行阶段。模型发现问题时直接修订权威规格、设计或计划，不让模型成为第二份需求正文。

本仓库遇到对象关系、归属规则和有限配置问题时可选 Alloy；跨步骤状态、并发和协议可选 TLA+、PlusCal 或 Quint。优先沿用已有工具；算法步骤适合 PlusCal，已有 Quint 模型时沿用 Quint，其他动态建模可从 TLA+ 评估。长期维护新模型前说明推荐与维护代价，必要时请用户决定。只有结构和动态行为是独立问题时才组合两类模型。不默认引入 StateRight 或绑定 Rust；已有需求时单独评估。模型检查器不加入 tao-dev 的运行依赖或分发包。

<!-- tao:field consequences -->
**影响与后果：** 需求保持易读且只有一份权威正文，无需同步自然语言、全局形式词汇与多个模型。建模可能发现需要修订规格、设计或计划的事实；可能改变设计结论的建模成果必须先于依赖它的实现完成，以 depends_on 表达依赖。它是本仓库的风险控制选择，不要求使用方执行固定文档或开发序列。

模型和常规测试都属于机器辅助检查，但结果要按各自实际能力说明。模型检查只说明声明的模型、检查规则、边界和配置内的结果，不证明模型完整、模型与实现一致或交付已经验收；实现层测试和实际验收仍要分别执行。新工具随对应 TASK 增量配置，模型检查生成的大量状态数据和临时输出默认不进入版本库。未来若出现需求阶段自动形式化、跨语言模型交换或绑定某种实现语言的明确需求，再通过新的规格和决定重新评估。
```
