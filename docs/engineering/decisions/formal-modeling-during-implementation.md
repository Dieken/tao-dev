# 保持自然语言需求，按风险在实施阶段建模

<!-- tao:section decisions -->
## 决策

```{adr} 保持自然语言需求，按风险在实施阶段建模
:id: ADR_20260927_NQCTSW9RG77YA2P4
:status: proposed
:links: REQ_20260914_4CS6P421MGW68PME, REQ_20260914_0J68SDKV86ENKER2

<!-- tao:field context -->
**背景与备选：** REQ 需要供用户、agent 和实现者直接阅读，也要能表达行为、质量、约束和业务规则。一种做法是把 REQ 改成结构化 EARS 或 FRETish，并在需求阶段维护形式化词汇和时序公式；另一种做法是保留自然语言需求，只在实施计划中为可能推翻方案的重要问题安排形式化建模。前一种做法会增加需求语法、解析工具、术语映射，以及多份必须保持一致的内容，但仍不能消除业务术语、环境假设和模型范围中的歧义。完全不提供建模指导则可能错过在大量编码前发现并发、状态和对象关系问题的机会。

<!-- tao:field decision -->
**选择：** REQ body 保持自然语言；EARS 只用于帮助作者写清主体、条件、响应和验收，不强制使用标准句式。不引入 FRETish、形式化 glossary 或需求阶段的形式模型。agent 在 plan 阶段按风险决定是否建立形式化建模 TASK，并在 implement 阶段优先执行；它与类型检查、测试、静态分析和代码实现使用相同的 TASK、依赖、验证和证据机制。模型发现需求、设计或计划问题时，通过已有 refine 流程修订权威文档，不让模型成为另一份需求或设计正文。

对象关系、归属规则和有限配置使用 Alloy；跨多个步骤的状态变化、并发和协议使用 TLA+、PlusCal 或 Quint 中的一种模型。项目已有工具时继续使用；过程适合用算法步骤描述时选 PlusCal，已有 Quint 模型时选 Quint，其他情况默认选 TLA+。模型需要长期维护且项目没有既定选择时，由 agent 向用户说明对当前问题的推荐和维护影响，并询问用户是否有偏好。只有结构和动态行为是两个独立问题时，才同时使用 Alloy 和一种动态模型。暂不采用 StateRight：tao-dev 面向多种实现语言，不把默认流程绑定到 Rust；项目已经使用或用户明确要求时再单独评估。模型检查器不加入 tao-dev 的运行依赖或分发包。

<!-- tao:field consequences -->
**影响与后果：** 需求保持易读、灵活，并且只有一份权威正文；项目不需要维护自然语言到公式的转换，也不需要让全局形式化词汇与多个模型保持一致。相应地，模型在 plan 批准后才建立，可能在 implement 中发现需要回退 spec、design 或 plan 的问题。为减少返工，可能改变设计结论的建模 TASK 必须在依赖它的实现工作之前完成，并用 `depends_on` 表达这种关系。

模型和常规测试都属于机器辅助检查，但结果要按各自实际能力说明。模型检查只说明声明的模型、检查规则、边界和配置内的结果，不证明模型完整、模型与实现一致或交付已经验收；实现层测试和实际验收仍要分别执行。新工具随对应 TASK 增量配置，模型检查生成的大量状态数据和临时输出默认不进入版本库。未来若出现需求阶段自动形式化、跨语言模型交换或绑定某种实现语言的明确需求，再通过新的规格和决定重新评估。
```
